# 影响范围

更新时间：2026-10-28。下面每个数字都来自本项目的实测或反汇编，可以自己复核。

## 一句话结论

- 缺陷在 **Sophisticated Core** 的服务端整槽转移处理器里：它把客户端给的槽位号直接交给
  `quickMoveStack`，而这条路径从不询问"这个槽位允许玩家取出吗"。过滤槽（幽灵槽）的
  `mayPickup` 恒为 `false`，但**这条路上没人问它**。
- **所有发布了这条消息的 Core 版本线都存在**。
- **运行时实测只做了 1.21.1 一条线**，用的是最新发行组合
  （Core `1.21.1-1.5.19.2434` + Backpacks `1.21.1-3.26.17.2232`，MC 1.21.1 / NeoForge 21.1.265）。
  实测结果：储物区 `0 → 1`，手上数量不变，重复 5 次 `+5`。
- 其他版本线是**代码级验证**（反汇编发行版 JAR，或读取该分支已发布的源码），**没有跑服务器**。
  这条区别在本文里始终分开写，不混用。

## "受影响"具体指什么

改装过的客户端可以发送 `transfer_full_slot`，携带一个过滤槽的下标。服务端接受该下标，把样板合并进
真实储物区。样板不被消耗，真实物品多出来一个。

**原版客户端做不到**：`StorageScreenBase` 的两个发送点都限定了必须是真实储物槽。

另有幽灵槽写入通道（`set_ghost_slot`），那是服务端配方查看器用来放样板的，属于**第二个问题**，
且与版本有关，见文末。

## 为什么不只是"源码这么写"

服务器真正跑的是 JAR。1.21.1 的处理器方法体共 113 行字节码：
`getSlot`（偏移 6）→ `quickMoveStack`（偏移 47），**整个方法里没有任何比较指令**
（`if_icmp` 数量 0，`iflt`/`ifge` 数量 0）。`quickMoveStack` 方法体 113 行，`mayPickup` 调用 0 次、
`IFilterSlot` 判断 0 次。而过滤槽类在 5 个 JAR 里的 `mayPickup` 都是 `iconst_0; ireturn`（恒 false）。

## 次级问题：幽灵槽写入

`set_ghost_slot` 是配方查看器放样板用的通道。部分版本是裸 `Slot.set`：

| 版本 | 处理器写法 |
| --- | --- |
| 1.18.2 发行 JAR | 仅判断菜单类型后 `getSlot(n).set(stack)` |
| 1.19.2 发行 JAR | 同上 |
| 1.20.1 及以后的发行 JAR | 走带校验的 `setGhostSlot(n, stack)` |
| 1.21.1 Core `1.4.18.1629` | 裸 `Slot.set`（1.5.x 起修复） |

所以次级问题影响 1.18.2、1.19.2，以及 1.21.1 上到 `1.4.18` 为止的版本；从 1.20.1 起、以及 Core `1.5.x`
起，该写入已带校验。它还需要服务端同时注册了配方查看器的幽灵槽消息才会生效。

## 本文不主张什么

- **不主张 1.21.1 以外的运行时复现**。只有 1.21.1 真跑了服务器。
- 不主张原版客户端能触发。它不能。
- 不针对任何具体服务器、玩家或作者动机。
- 不主张 Backpacks 本身是缺陷所在。Backpacks 提供菜单和过滤槽，未校验的处理器在 Core 里。

## 修复

上游 PR 里的两条件守卫能堵住转移路径，且实测不影响普通储物转移与合成槽。
`backpack-transfer-fix` 1.2.0 用外部 Mixin 在 1.21.1 线上实现了同样的守卫，同时覆盖该线上旧 Core 的
裸幽灵槽写入。

其他版本线的类名不同（`TransferFullSlotMessage`、`TransferFullSlotPacket`），需要单独编译；
**不要把 1.21.1 的修复包装到 1.20.1 或更早的服务器上**。
